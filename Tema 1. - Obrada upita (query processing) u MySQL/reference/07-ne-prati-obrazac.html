Gde MySQL ne prati obrazac

Tri negativne tvrdnje sa tačnim granicama, izvorima i merenjima. Ovo je jedino poglavlje koje predavanja ne pokrivaju — svaka tvrdnja mora da stoji sama.

1 · Tri tvrdnje, u jednoj tabeli

§6.1 vektorizacijaNema je. Read() vraća jednu torku po pozivu. Cena: ~20 ns po torki po predikatu, nezavisno od selektivnosti.
§6.2 paralelizamIma ga, ali samo u motoru. Paralelno čitanje klasterovanog indeksa za nezaključavajući COUNT(*). Plan nikada nije paralelan.
§6.3 keširanjeNema deljenog keša plana, nema keša rezultata upita od 8.0, ima sesijski keš pripremljene naredbe.

2 · Vektorizacija: brojevi za poređenje

MySQL 8.41 torka po pozivu operatora — model iteratora
PostgreSQL1 torka po pozivu — ni on ne vektorizuje
DuckDB2.048 torki (STANDARD_VECTOR_SIZE), kolonarno
ClickHouse1.024–4.096 torki, uz SIMD nad paketom
HeatWavezaseban izvršilac: kolonarno skladištenje + vektorizacija + više čvorova

Vektorizacija ≠ paralelizam. Vektorizacija je više torki po pozivu u jednoj niti. Paralelizam je više niti. Nezavisne osobine.

3 · Paralelizam: tri uslova i jedan šav

innodb_parallel_read_threadssesijska, dinamička, podrazumevano 4; vrednost preko 256 se odseca na 256
uslov 1upit mora biti nezaključavajući COUNT(*) (WL#11720)
uslov 2mora se čitati klasterovani indeks — otuda FORCE INDEX(PRIMARY)
uslov 3nijedan predikat — jedna WHERE klauzula gasi sve
izmerenobez WHERE: 2,9× (1 → 16 niti). Sa WHERE: 1,01×, tj. ništa.

Zašto baš tu granica: paralelno čitanje je posao motora, ispod handler API-ja. Bez predikata i projekcije InnoDB sam izbroji torke u podstablima i vrati serverskom sloju samo zbir. Sa predikatom o torki odlučuje iterator iznad šava, pa svaka torka mora da pređe granicu pojedinačno, u jednoj niti.

paralelizam na nivou upitaPostgreSQL: optimizator ugrađuje radne niti u sam plan

4 · Keširanje: tri stvari koje se ne smeju mešati

keš rezultata upita (query cache)čuvao rezultate · zastareo 5.7.20 · uklonjen u 8.0
deljeni keš planačuvao bi planove između sesija (Oracle-ov deljeni pul) · ne postoji
keš pripremljene naredbečuva unutrašnju strukturu naredbe · postoji, sesijski

Šta je „unutrašnja struktura": stablo raščlanjivanja, razrešene kolone (* razvijeno u listu), tabela simbola. Nije plan izvršenja: ni izbor indeksa, ni redosled spoja, ni procene cene.

Dva merljiva dokaza

plan se ne keširatri EXECUTE-a iste naredbe → tri zasebna traga, sa različitim procenama i cenama, jer se optimizuje nad stvarnom vrednošću parametra
naredba se kešira, sesijskiEXECUTE u drugoj sesiji → ERROR 1243 (HY000); ALTER TABLE → Com_stmt_reprepare ide 0 → 1
-- Zamka: SET naredbe se i same traguju. Sve @promenljive PRE ukljucivanja traga.
SET @a='DE', @b='US', @c='JP';
SET SESSION optimizer_trace_offset=-3, SESSION optimizer_trace_limit=3;
SET SESSION optimizer_trace='enabled=on';
EXECUTE s USING @a; EXECUTE s USING @b; EXECUTE s USING @c;
SET SESSION optimizer_trace='enabled=off';
SELECT QUERY, LENGTH(TRACE) FROM information_schema.OPTIMIZER_TRACE;

Ponovna priprema se pokušava najviše tri puta; posle toga greška. Okidači su promene metapodataka (ALTER, DROP, TRUNCATE, ANALYZE, FLUSH TABLES) — ne i promene sadržaja (INSERT, UPDATE).
