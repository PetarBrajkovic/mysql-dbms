# Install MySQL 8.4, Workbench, and the sample datasets

Type: task
Status: resolved

## Question

Nothing to decide - this unblocks every chapter that needs real query output. HITL: the user drives
the installers; the agent prepares and verifies the data.

Required:
1. **MySQL 8.4 LTS Community Server** (Windows MSI). `EXPLAIN ANALYZE` needs 8.0.18+; 8.4 is the
   current LTS.
2. **MySQL Workbench** - needed for **Visual Explain**, which renders execution plans as annotated
   diagrams. This is the single best source of the "pictures of SQL queries" the professor asked for.
3. **Sakila** sample database, loaded and verified.
4. A **synthetic wide table** of several million rows, generated by a script kept in
   `examples/00-setup/`. Sakila is too small to force interesting optimizer decisions - table scans
   win trivially and the parallel/scan chapters would have nothing to show.

## Answer

- **MySQL Server 8.4.11** (Windows, LTS), **MySQL Workbench 8.0.47** - both user-installed and
  verified live (`SELECT VERSION();` -> `8.4.11`).
- **Sakila** loaded and verified: `SELECT COUNT(*) FROM sakila.film;` -> `1000`.
- **Synthetic wide table**: `obrada_upita.wide_events`, generated by the four scripts in
  `examples/00-setup/` (`01-schema.sql`, `02-generate.sql`, `03-index-and-analyze.sql`,
  `04-verify.sql`, run in that order - see the folder's `README.md`).
  - **5,000,000 rows**, ~19 columns, **2,112.5 MB** total (1,394.0 MB data + 718.5 MB indexes).
  - Seven indexes present as designed: `PRIMARY (id)`, `idx_event_type`, `idx_country_code`,
    `idx_customer_id`, `idx_is_flagged`, `idx_created_at`, `idx_customer_created`
    `(customer_id, created_at)`, `idx_status_created (status, created_at)`.
  - `country_code` skew verified exactly as designed: **US = 70.0%** (3,500,177 rows), the
    remaining 14 countries roughly uniform (~2.1-2.2% each).
  - `idx_customer_id` behaves as intended: `EXPLAIN SELECT * ... WHERE customer_id = 12345`
    picks it with `type: ref`, estimated **29 rows**.
  - **One real correction to the setup's own prediction**, worth carrying into chapter 4:
    `EXPLAIN SELECT COUNT(*) ... WHERE country_code = 'US'` was expected to force a full table
    scan given the 70% skew, but the live server picked `type: ref` on `idx_country_code` for
    **both** `'US'` (est. 2,454,588 rows) and the rare `'JP'` (est. 213,948 rows), with
    `Extra: Using where; Using index` in both cases. Reason: `COUNT(*)` is answered entirely
    from the secondary index - a skinny index-only scan beats a table-scan of this wide row
    regardless of selectivity. Selectivity only decides the access path once the query needs
    columns the index doesn't cover; `03-index-and-analyze.sql` and `04-verify.sql` have been
    corrected in place to say this, with a non-covering query left for chapter 4 to try
    instead.
  - A second bug hit and fixed **during** generation, not just prediction: `RAND()` referenced
    three times against the same derived-table alias got re-evaluated per reference because
    MySQL merged/inlined the derived table instead of materializing it, occasionally driving
    `ELT()`'s index to 0 (-> `NULL`) and failing `country_code`'s `NOT NULL` constraint. Fixed
    with the standard `LIMIT` trick to force materialization - see the comment in
    `02-generate.sql`. Worth remembering for any future synthetic-data script: a derived table
    with a non-deterministic expression referenced more than once needs to be forced to
    materialize, or every reference silently redraws.
- **Connection**: local `MySQL84` Windows service, default `localhost:3306`, `root` user,
  password known only to the user (never shared with the agent).
