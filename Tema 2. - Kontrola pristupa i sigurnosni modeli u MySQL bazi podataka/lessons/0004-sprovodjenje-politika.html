Lekcija 04 · Poglavlje 5 (Sprovođenje bezbednosnih politika)

Autentifikacija je zamenljiva, sprovođenje politike nije

Prethodna lekcija je pokazala da pogled nije mehanizam autorizacije nego imenovani predikat. Ova zatvara srodno pitanje jedan nivo niže: kad server donese neku odluku o bezbednosti, ko je tačno donosi — jezgro servera, učitana komponenta ili autentifikacioni plugin.

Veza sa ciljem Poglavlje 5 ne sme biti spisak mehanizama. Njegova okosnica je jedan kriterijum, i kad završiš ovu lekciju treba da umeš, bez podsetnika: (1) da kažeš šta autentifikacioni plugin vidi a šta ne vidi, (2) da za bilo koji mehanizam iz poglavlja odrediš tačku sprovođenja iz prve, i (3) da objasniš zašto je Enterprise Firewall jedini koji ne staje u taj kriterijum.

1 · Faza 1 bira tačno jedan red

Nalog u MySQL-u nije korisnik nego par 'ime'@'host' — jedan red u mysql.user (Lekcija 02). Kad se klijent poveže, više redova može odgovarati istoj konekciji: 'doc'@'localhost' i 'doc'@'%' oba se poklapaju sa prijavom sa same mašine servera. Server tada ne spaja ništa.

Whenever the server reads the user table into memory, it sorts the rows. When a client attempts to connect, the server looks through the rows in sorted order. The server uses the first row that matches the client host name and user name. MySQL 8.4 Reference Manual, 8.2.4 Access Control, Stage 1: Connection Verification

Sortiranje ide od najspecifičnijeg hosta ka najširem. „Specifičnije" ovde ne znači „detaljnije zapisano" nego obuhvata manje mašina:

192.168.1.7jedna mašina — najspecifičnije, prvo u redosledu
192.168.1.0/24256 mašina, CIDR notacija
192.168.1.0/255.255.255.0256 mašina, mrežna maska
%bilo koji host
''takođe bilo koji host, ali sortira iza %

Unutar istog hosta neanonimni korisnici sortiraju pre anonimnih. Redosled nije proizvoljan: pošto server staje na prvom poklapanju i nikad se ne vraća na širi red, obrnut redosled bi značio da 'doc'@'%' uvek pobeđuje, pa izuzetak za pojedinačnu mašinu ne bi mogao ni da postoji.

Česta zabluda OR-kompozicija nivoa — (global − restrictions) OR db OR table OR column OR routine — je pravilo Faze 2 i kombinuje nivoe unutar naloga. Pri izboru reda u Fazi 1 nema nikakvog OR-a: bira se jedan red i tu se staje.

1a · Ali šta tačno taj jedan red određuje

Ovde je lako preterati sa zaključkom, i to je najvažnija zamka celog poglavlja. Izbor reda u Fazi 1 određuje autentifikaciju i globalne privilegije — ali ne i privilegije nad bazom, tabelom ili kolonom. Za njih Faza 2 radi svoje, potpuno nezavisno poklapanje:

The server looks in the db table for a match on the Host, Db, and User columns. The Host and User columns are matched to the connecting user's host name and MySQL user name. … The wildcard characters % and _ can be used in the Host and Db columns. MySQL 8.4 Reference Manual, 8.2.7 Access Control, Stage 2: Request Verification

Posledica je neočekivana i izmerena je na ovom serveru: GRANT SELECT ON poliklinika.* TO 'probni'@'%' upisuje red u mysql.db sa Host = '%', a % se poklapa i sa klijentom koji dolazi sa localhost. Privilegija, dakle, stiže iz reda kojim se nisi autentifikovao.

koji plugin, koja lozinka, REQUIRE, zaključanost, globalne privilegije isključivo iz jednog reda izabranog u Fazi 1
privilegije nad bazom / tabelom / kolonom sopstveno poklapanje u mysql.db i mysql.tables_priv, po hostu klijenta, sa džokerima

Zato uži red sa samo USAGE zaklanja širi red samo na globalnom nivou. I zato CURRENT_USER() ne prikazuje domet sesije: on imenuje red iz Faze 1, a privilegije mogu doći iz drugog reda. To je isti obrazac kao CURRENT_ROLE() iz Lekcije 02, koji ne prikazuje nasleđene uloge.

Probaj u Workbench-u

Preduslov: nalog sa privilegijom CREATE USER (na ovom serveru: root). Napravljeni nalozi se brišu na kraju bloka, baza poliklinika se ne menja.

Pokreni ovo

-- Siri red sme da cita, uzi red nema nista.
CREATE USER 'probni'@'%'
  IDENTIFIED BY 'Lozinka!2345';
CREATE USER 'probni'@'localhost'
  IDENTIFIED BY 'Lozinka!2345';
GRANT SELECT ON poliklinika.* TO 'probni'@'%';

-- Sada otvori NOVU konekciju kao 'probni' i pokusaj:
--   SELECT * FROM poliklinika.patients LIMIT 1;

DROP USER 'probni'@'%', 'probni'@'localhost';

Šta treba da vidiš

probni@localhost   1   1   Pacijent 001   1967-12-23

Pazi: upit mora da se izvrsi iz konekcije prijavljene kao probni. Iz privilegovane konekcije dobija se 1146 (Table ... doesn't exist), sto meri nesto sasvim drugo.

Kako se ovo čita: dva nalaza u jednom redu rezultata. CURRENT_USER() je probni@localhost — Faza 1 je izabrala uži red, baš kao što odeljak 1 tvrdi. A SELECT ipak uspeva, jer privilegija nad bazom ne dolazi iz tog reda nego iz mysql.db, gde stoji Host = '%'. Provera: SELECT Host, Db, User, Select_priv FROM mysql.db WHERE User = 'probni'; vraća % / poliklinika / probni / Y, uz prazan @@mandatory_roles. Izmereno na 8.4.11.

2 · Šta autentifikacioni plugin vidi

Ne dokazuju se svi nalozi na isti način: jedan lozinkom, drugi preko LDAP direktorijuma, treći preko naloga operativnog sistema, četvrti Kerberosom. Da je provera ušivena u server, svaki novi način dokazivanja identiteta tražio bi novu verziju servera. Zato je način provere izdvojen u zamenljiv modul i upisan u sam nalog, u kolonu plugin tabele mysql.user. Podrazumevani modul u 8.4 je caching_sha2_password; stariji mysql_native_password je zastareo u 8.0.34, isključen u 8.4 i uklonjen u 9.0.

The server then authenticates the client, determining from the account row which authentication plugin applies to the client: … the server invokes that plugin to authenticate the user, and the plugin returns a status to the server indicating whether the user provided the correct password and is permitted to connect. MySQL 8.4 Reference Manual, 8.2.17 Pluggable Authentication

Važno je i ono što tu ne piše. Plugin ne bira red — server ga je već izabrao i iz njega pročitao koga da pozove. Plugin dobija dve vrednosti, kredencijal koji je klijent poslao i sačuvani authentication_string, i vraća jedan bit. Redosled u Fazi 1 to pokazuje sam:

jezgrosortira redove i bira jedan, po hostu i imenu
jezgroiz kolone plugin tog reda vidi koga da pozove
pluginkredencijal naspram authentication_string → jedan bit
jezgrozaključanost, REQUIRE, istek lozinke, brojači

Plugin je u sredini i okružen jezgrom sa obe strane. Priručnik čak precizira i redosled poslednja dva koraka: „The server checks credentials first, then account locking state." Zaključan nalog sa tačnom lozinkom, dakle, prolazi kroz plugin uspešno — pa ga jezgro odbije odmah posle, greškom ER_ACCOUNT_HAS_BEEN_LOCKED.

3 · Kriterijum

Plugin ima najsiromašniji ulaz u sistemu: dve vrednosti i nikakvo pamćenje između poziva. Odatle sledi kriterijum celog poglavlja:

Kriterijum Jezgro je jedino koje čita stanje. Plugin i komponenta sude isključivo o vrednostima koje im jezgro preda. Svaka odluka kojoj treba bilo šta osim „poklapa li se ovaj kredencijal sa ovim otiskom" nije odluka plugina.
tajna naspram otiskaulaz plugina → plugin
account_locked, ssl_type, password_expiredkolone izabranog reda → jezgro
broj uzastopnih promašaja, potrošnja po satubrojači jezgra → jezgro
mysql.password_historytabela koju modul ne čita → jezgro
koji plugin uopšte pozvatikolona plugin → jezgro

Kriterijum govori o stanju, ne o trenutku. Dve provere mogu se desiti u istom trenutku a pripadati različitim mestima: „ima li lozinka cifru" traži samo tekst lozinke, dok „da li je među poslednje tri" traži redove iz mysql.password_history.

4 · Treće mesto: komponenta

Zahtev „lozinka mora imati najmanje 12 znakova, veliko i malo slovo, cifru i specijalni znak" ne može se proveriti pri prijavi — tada server ima samo otisak, iz kog se sastav ne vidi. Odluka mora pasti u trenutku postavljanja lozinke, a tada plugin ne radi. MySQL zato otvara treće mesto: komponentu, modul koji jezgro poziva kad mu zatreba sud o vrednosti.

The validate_password component serves to improve security by requiring account passwords and enabling strength testing of potential passwords. … validate_password checks the password against the current password policy and rejects the password if it is weak (the statement returns an ER_NOT_VALID_PASSWORD error). This applies to the ALTER USER, CREATE USER, and SET PASSWORD statements. MySQL 8.4 Reference Manual, 8.4.3 The Password Validation Component
Probaj u Workbench-u

Preduslov: nalog sa privilegijom za INSTALL COMPONENT (na ovom serveru: root). Komponenta ostaje učitana i kroz restart servera dok se izričito ne ukloni — poslednja naredba je vraća u prvobitno stanje.

Pokreni ovo

INSTALL COMPONENT 'file://component_validate_password';

SHOW VARIABLES LIKE 'validate_password%';

CREATE USER 'slaba'@'localhost'
  IDENTIFIED BY 'abc';

UNINSTALL COMPONENT 'file://component_validate_password';

Šta treba da vidiš

validate_password.policy                        MEDIUM
validate_password.length                        8
validate_password.mixed_case_count              1
validate_password.number_count                  1
validate_password.special_char_count            1
validate_password.check_user_name               ON
validate_password.dictionary_file
validate_password.changed_characters_percentage 0

Error Code: 1819. Your password does not satisfy the current policy
requirements

Kako se ovo čita: nalog nije ni nastao. Odluku nije doneo nijedan autentifikacioni plugin — oni u ovom trenutku ne rade — nego komponenta, pozvana iz jezgra nad tekstom lozinke. Greška 1819 je ER_NOT_VALID_PASSWORD. Promenljiva validate_password.policy određuje koliko se ostalih uopšte primenjuje: LOW gleda samo dužinu, MEDIUM (podrazumevano) dodaje sastav znakova, STRONG dodaje i rečnik iz dictionary_file.

Razlika u jednoj rečenici: plugin odgovara na pitanje „da li si ti taj", komponenta na pitanje „da li je ova vrednost prihvatljiva". Prvi gleda identitet, druga podatak; nijedno od to dvoje ne odlučuje o pristupu objektu, što ostaje Faza 2.

validate_password ima i opcije koje deluju kao da poznaju nalog — check_user_name i changed_characters_percentage. Ne poznaju ga: jezgro joj i korisničko ime i tekuću lozinku prosleđuje kao ulaz. Komponenta nikada sama ne čita mysql.user ni mysql.password_history.

5 · Tri porodice politika kao dokazi

Od cele porodice politika o lozinkama, samo provera jačine je komponenta. Sve ostalo traži stanje naloga, pa je u jezgru.

jačina lozinkevalidate_password.* → komponenta
istekdefault_password_lifetime (podrazumevano 0 = nikad), PASSWORD EXPIRE INTERVAL 90 DAY
ponovna upotrebaPASSWORD HISTORY 5, PASSWORD REUSE INTERVAL 365 DAY
dvostruka lozinkaRETAIN CURRENT PASSWORD / DISCARD OLD PASSWORD
nasumična lozinkaIDENTIFIED BY RANDOM PASSWORD

Istek lozinke nije odbijanje veze nego ograničeni režim: nalog se poveže, ali svaka naredba osim promene lozinke pada.

mysql> SELECT 1;
ERROR 1820 (HY000): You must reset your password using ALTER USER
statement before executing this statement.

Dvostruke lozinke rešavaju problem koji vredi imenovati u radu. Kad deset aplikacija na deset servera koristi isti nalog, lozinka se ne može promeniti svuda u istom trenutku. RETAIN CURRENT PASSWORD čini staru lozinku sekundarnom — obe rade istovremeno — pa se aplikacije prebacuju jedna po jedna, a tek na kraju ide DISCARD OLD PASSWORD. Za sopstveni nalog traži privilegiju APPLICATION_PASSWORD_ADMIN, za tuđe naloge CREATE USER.

Politika naloga. FAILED_LOGIN_ATTEMPTS 3 PASSWORD_LOCK_TIME 1 znači tri uzastopna promašaja i jedan dan zaključanosti; tačna lozinka resetuje brojač. Ručno zaključavanje je ACCOUNT LOCK / ACCOUNT UNLOCK.

Probaj u Workbench-u i u komandnoj liniji

Preduslov: root za CREATE USER. Koraci sa prijavljivanjem moraju ići kroz mysql u komandnoj liniji — Workbench kešira konekciju, pa pokušaji ne bi bili zasebne prijave. Nalog se briše na kraju.

Pokreni ovo

CREATE USER 'kljucar'@'localhost'
  IDENTIFIED BY 'Lozinka!2345'
  FAILED_LOGIN_ATTEMPTS 3
  PASSWORD_LOCK_TIME 1;

SELECT user, host,
       JSON_EXTRACT(User_attributes, '$.Password_locking') AS zakljucavanje
FROM mysql.user WHERE user = 'kljucar';

-- Zatim u cmd: tri puta POGRESNA lozinka, pa cetvrti put TACNA.
--   mysql -u kljucar -h 127.0.0.1 -p

ALTER USER 'kljucar'@'localhost' ACCOUNT UNLOCK;
DROP USER 'kljucar'@'localhost';

Šta treba da vidiš

kljucar | localhost | {"failed_login_attempts": 3, "password_lock_time_days": 1}

ERROR 3955 (HY000): Access denied for user 'kljucar'@'localhost'.
Account is blocked for 1 day(s) (1 day(s) remaining)
due to 3 consecutive failed logins.

Kako se ovo čita: Četvrta prijava je išla sa tačnom lozinkom. Plugin je, dakle, rekao „da", a veza je svejedno odbijena — jezgro je pročitalo stanje koje plugin ne vidi, i poruka to i kaže: govori o brojaču promašaja, ne o lozinci. Posle ACCOUNT UNLOCK ista, nepromenjena lozinka prolazi, čime je lozinka isključena kao uzrok. Politika je pritom JSON upisan na sam nalog — isti obrazac kao partial_revokes iz Lekcije 02.

Za citiranje: broj 3955 je izmeren na 8.4.11. Priručnik u svom primeru prikazuje 3957, uz formulaciju „an error that looks like this" — dakle ilustraciju, ne specifikaciju. Ručno zaključan nalog daje drugu poruku (ER_ACCOUNT_HAS_BEEN_LOCKED, „Account is locked.").

Resursna ograničenja idu kroz WITH MAX_QUERIES_PER_HOUR 1000 MAX_USER_CONNECTIONS 5: granice stoje u kolonama reda naloga, brojači su u memoriji, kreću od nule pri pokretanju servera i ne prenose se kroz restart, a FLUSH USER_RESOURCES ih nuluje. Prekoračenje vraća grešku 1226.

Politika veze. REQUIRE SSL, REQUIRE X509, SUBJECT, ISSUER, CIPHER — sve kolone izabranog reda. Tu je i kontrola pristupa po hostu iz odeljka 1, kao i skip_networking=ON, koje isključuje TCP/IP u potpunosti.

Za pisanje poglavlja REQUIRE se ne proverava „tokom TLS rukovanja, pre Faze 1", kako se ponekad navodi. To je svojstvo naloga i ne može se proveriti dok nalog nije izabran: TLS rukovanje jeste ranije, ali odluka da li baš ovaj nalog sme bez šifrovane veze pripada jezgru, unutar Faze 1.

6 · Enterprise Firewall, jedini izuzetak

Komercijalno MySQL Enterprise Firewall je deo komercijalnog izdanja MySQL Enterprise Edition. U radu se navodi kao teorija i izričito označava kao komercijalan, bez demonstracije.
MySQL Enterprise Edition includes MySQL Enterprise Firewall, an application-level firewall that enables database administrators to permit or deny SQL statement execution based on matching against lists of accepted statement patterns. … Each MySQL account registered with the firewall has its own statement allowlist. MySQL 8.4 Reference Manual, 8.4.7 MySQL Enterprise Firewall

Svi dosadašnji mehanizmi odlučuju na osnovu identiteta ili objekta. Firewall odlučuje na osnovu oblika same naredbe: nalog se prvo pusti u režim učenja, napravi se spisak dozvoljenih obrazaca, i posle toga naredba koja ne liči ni na jedan obrazac biva odbijena — i kad nalog ima svaku potrebnu privilegiju.

Zato je zanimljiv za rad: SQL injekcija ne krši nijednu privilegiju. Napadnuta aplikacija radi pod svojim potpuno legitimnim nalogom, i ni subjekat ni objekat se nisu promenili — promenila se samo naredba. DAC sudi o paru (subjekat, objekat) i taj napad mu je po konstrukciji nevidljiv.

7 · Provera

Šest pitanja, po jedno na svaku netrivijalnu tvrdnju lekcije. Odgovori napamet, bez vraćanja na tekst — vrednost je u naporu prisećanja, ne u tačnom rezultatu iz prvog pokušaja.

1. Postoje redovi 'app'@'192.168.1.7', 'app'@'192.168.1.0/24' i 'app'@'%'. Klijent dolazi sa 192.168.1.7. Šta server koristi?

Sortiranje ide od najužeg obuhvata ka najširem i server staje na prvom poklapanju. Reč je o izboru reda u Fazi 1 — dakle o autentifikaciji i globalnim privilegijama; privilegije nad bazom se traže posebno (pitanje 7).

2. Zašto server sortira redove od najužeg hosta ka najširem?

Pošto se staje na prvom poklapanju, redosled je jedini način da izuzetak uopšte postoji; rezervnog pokušaja nema.

3. Nalog ima REQUIRE X509, a klijent se povezuje bez sertifikata ali sa tačnom lozinkom. Ko odbija vezu?

REQUIRE je stanje upisano u red naloga, a stanje čita samo jezgro.

4. Zašto FAILED_LOGIN_ATTEMPTS ne može biti posao plugina?

Plugin je funkcija bez pamćenja između poziva; brojač je stanje, dakle jezgro.

5. Zabrana ponovne upotrebe poslednjih N lozinki — gde se odlučuje?

Kriterijum govori o potrebnom stanju, ne o trenutku: obe provere su pri postavljanju lozinke, ali samo jednoj treba istorija naloga.

6. Po čemu se Enterprise Firewall razlikuje od ostalih mehanizama poglavlja?

Uvodi dimenziju koju DAC nema, pa hvata napad u kom su i subjekat i objekat legitimni.

7. Postoje 'probni'@'%' sa GRANT SELECT ON poliklinika.* i 'probni'@'localhost' bez ijedne privilegije. Klijent se prijavi sa iste mašine i pokrene SELECT nad tom bazom.

Faza 2 ne koristi red izabran u Fazi 1: ona sama traži poklapanje u mysql.db, po hostu klijenta i sa džokerima. Izmereno na 8.4.11.

Rezultat: 0 / 0
