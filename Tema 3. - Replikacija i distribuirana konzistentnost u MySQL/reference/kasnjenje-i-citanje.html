Kašnjenje replikacije, njegovo merenje i čekanje sopstvenog upisa

Sažetak lekcije 07. MySQL 8.4.11, naša topologija 3307/3308/3309.

Definicija

lag(T) = t2 - t0          // both phases always count
t0  COMMIT on source       ORIGINAL_COMMIT_TIMESTAMP  (source clock, carried in the binlog)
t1  queued in relay log    LAST_QUEUED_TRANSACTION_END_QUEUE_TIMESTAMP  (replication_connection_status)
t2  applied, visible       LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP (replication_applier_status_by_worker)
raspodela na fazemerenje, ne definicija. Loopback: prijem 0,724 ms, ukupno 6,375 ms (≈ 89 % primena)
izvor kašnjenja kod nasnit primene. Prirodni nalet: relay log je stao na 4,5 s, a kašnjenje je raslo do 31,0 s

Seconds_Behind_Source = sat replike − t₀ događaja u niti primene

slabost 1ne vidi fazu prijema: spora mreža → 0 dok replika kasni („useful only for fast networks“)
slabost 2dva sata; razlika se računa kad se pokrene nit prijema; kasniji pomeraj sata replike ide u rezultat sa istim znakom (negativno → 0)
slabost 3više niti primene (podrazumevano 4): zasniva se na Exec_Source_Log_Pos, a ne na poslednjoj komitovanoj transakciji
ostalocele sekunde; bez posla → 0; NULL ako nit primene ne radi
izmerenopri pražnjenju precenjuje do 4,2 s; na replici koja je stigla izvor (2 ms) pokazuje 1 u 31/360 uzoraka

performance_schema

rešavaslabost 1 (prijem ima t₁), slabost 3 (red po niti, sa GTID-om), rezoluciju (µs)
ne rešavaslabost 2: i ona oduzima sat izvora od sata replike. Preciznost ≠ tačnost. Kod nas je jedan sat, pa je greška nula po konstrukciji

Anomalije (asinhrona replika, SOURCE_DELAY = 3, izazvano)

read-your-writesupis na 3307 → SELECT na 3309: stara vrednost; GTID u RECEIVED_TRANSACTION_SET, nije u gtid_executed
monotona čitanjabez sopstvenog upisa: 3308 → nova vrednost, zatim 3309 → stara
Group ReplicationBEFORE zatvara prozor (lekcija 05); ovde se samo upućuje napred

Čekanje sopstvenog upisa

-- on the source, right after COMMIT: the name of the write (or session_track_gtids)
-- on the replica:
SELECT WAIT_FOR_EXECUTED_GTID_SET(@g, 2);   -- 0: applied -> read here; 1: timeout -> read the SOURCE
SELECT SOURCE_POS_WAIT(@file, @pos, 2);     -- same by address; -1 timeout; NULL if applier stopped
timeout = 0čekaj zauvek (podrazumevano; proizvoljna odluka). Provera bez čekanja: GTID_SUBSET(g, @@GLOBAL.gtid_executed)
izmereno0 posle 4 009 ms; timeout 1 → 1 posle 1 001 ms, i čitanje ostaje zastarelo; SOURCE_POS_WAIT 1 posle 4 312 ms
nit primene stojiGTID funkcija čeka ceo timeout, pa vrati 1; SOURCE_POS_WAIT odmah vrati NULL
GTID ili adresaadresa važi samo u logu jednog izvora (posle failovera ne važi); GTID važi svuda
ko plaćačitalac, oko jedno kašnjenje; upis je nepromenjen
MySQL Routeraccess_mode=auto, wait_for_my_writes; posle wait_for_my_writes_timeout čita sa izvora

Šta se ne skalira

upisisvaka replika ponavlja svaki upis; refman: „high number of reads and low number of writes“
nit primeneW > A → zaostatak raste za W − A u sekundi, na svakoj replici. Pomaže samo veće A (više niti za nezavisne transakcije, brži disk)
naletizvor 2 000 transakcija za 598 ms (≈ 3 300/s), jedna nit primene ≈ 60/s → nagib ≈ 1 s/s
